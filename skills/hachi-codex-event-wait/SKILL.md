# Hachi Codexイベント待機

**CLIで検知 → pending中のLunaへtool結果 → 親へ送信 → 終了済み親の新turn**を別々に確認する。
sleepで時間を経過させることは看板監視ではない。既存の`hachi task await`を待ち、独自の状態取得ループを作らない。

## 読む場所

手順・CLI例・Lunaへの依頼テンプレート・停止条件は
[Codexイベント待機runbook](../../runbooks/codex-event-wait.md)
を正本とする。別ホストではHachi運用正本内の同じ相対パスを解決する。
運用契約の参照先もそこから引き、長い過去の研究記録を毎回読み直さない。

## 最初に決めること

- 対象board、tenant/担当scope、親の現在のApp task ID、再利用する通知タスク、専用cursor、証跡保存先。
  元の実験のIDをコピーしない。会話と現状から分かる値を使い、不足値だけ質問する。
- 「実際のtask終端を一回待つ」か「終了済み親への通知まで試す」かを区別する。
  session全般・質問・stall監視は別の権限付き経路が必要。
- 通知タスクは既存の一つを再利用する。新しいApp taskはユーザーが作成を明示依頼した場合だけ。
  Lunaは通知担当であり、実装・設計判断・親のinbox claimを委譲しない。

## 現在の受入範囲（2026-09-10）

Lunaで600秒の単一pending MCP呼出しは実測成功。実Hachi awaitの既終端出力も別に取得済み。
**実Hachiの将来の状態変化から、承認操作なしに終了済み親を起こす全経路は未検証。**
親への送信は過去試験で手動承認を要した。スキルの導入を送信権限の追加とみなさない。

## 実行と判定

1. runbookの前提を一度確認し、対象を埋めた依頼テンプレートを既存通知タスクへ送る。
2. 正式CLIを一つのpending呼出しで待つ。親からの定期状態確認はしない。
3. イベントまたは実行異常でのみ結果を処理する。無変化・期限切れで自動再アームしない。
4. 親の再開を試した場合は、同じ親IDの新turnとイベントの対応を一度照合する。
   send受付、ローカルファイル作成、parent自身のpending解除だけをcold wake成功にしない。

設定変更は必要なtimeoutキーに限定する。送信承認・sandbox・他taskへ効く権限は黙って変更しない。
本スキルを読んだだけで監視を起動したとは報告せず、設定・投入・pending・検知・送信・親再開の実績を分けて伝える。
