## 2026-07-05: 契約セクション採番の衝突（並行オーケストレーター）

- 夜間セッションが契約 §32-§35 を起草・実装中に、別セッションが §32（画像アーティファクト）を
  先に main へマージし、採番衝突とマージコンフリクトが発生した（解決: 先着の main 側が正、
  当夜分を §33-§36 へ改番。コード内の契約参照 35ファイルを機械リマップ + 混在ファイルは手動修正）。
- 教訓: 並行オーケストレーターが動く環境では、**契約の § 採番は「main に先着した側が正」**。
  長時間のブランチ作業では (a) merge 直前に main の契約見出しを必ず再確認する、
  (b) 起票文・引き継ぎ文に将来の § 番号を固定で書かない（「起草時点の契約末尾に従う」と書く）、
  (c) 稼働中チェックアウト（main）では絶対にコンフリクト解決をせず、worktree 側に main を
  取り込んで解決してから戻す（supervisor/web は main から tsx ソース実行しているため、
  コンフリクトマーカー付きの作業ツリーは次回再起動を壊す）。

## 2026-07-02: レビュー反復の停止規則

- 初回コミット前の codex レビューを16巡実施し、ユーザーから「過剰な修正」と是正を受けた。
- 教訓: 1万行級の差分では LLM レビュアーは毎回新しい P1 を報告するため、「P0/P1 ゼロまで反復」は
  停止しない終了条件。反復に入る前に停止規則（最大巡数 or 実害基準）を宣言し、
  設計前提外（多重プロセス競合・監査精度・性能）の指摘は follow-up 化して基準線のコミットを優先する。
- 「動く基準線を早くコミット → 以降は小差分レビュー」の方が総コストが低い。
